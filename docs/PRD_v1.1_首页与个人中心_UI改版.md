## 1. Problem Statement

v1.0 的首页与个人中心已在 App 内落地并通过 Round 2 还原度评审，但 Boss 审视 Ardot 设计稿后发现 **5 处产品性问题**，其中 2 处会直接损害核心体验：

| # | 问题 | 性质 | 影响 |
|---|---|---|---|
| P1 | **柱状图「目标 1800」被读成"本周目标"** | 产品表述缺陷 | 目标每天可改（1800→1500→1900），单一水平线在语义上天然误导；用户会质疑"这条线到底准不准" |
| P2 | **首页有 2 个"新增食物"入口**（底部悬浮大加号 + 拟新增的右上角加号） | 交互冗余 | 入口不唯一，且在小屏手机上底部悬浮按钮遮挡餐次列表尾行 |
| P3 | **个人中心「查看全部 30 天记录 ›」是一个没有落地的页面** | 死链 | 点击无响应；该行本身造成三行历史下方的视觉空白 |
| P4 | **首页食物条目 100% 是纯文字，347 张精美食物图一张未用** | 颜值资产浪费 | 本项目核心卖点是"颜值程序"，首页主列表却是灰字，与定位矛盾 |
| P5 | **「添加食物」Sheet 只覆盖"奶茶"一种形态**（分量 3 档 + 甜度 5 档） | 适用范围缺口 | v1.0 食物库有 347 条，其中绝大多数非饮品，这些食物打开 Sheet 会看到无意义的分量档/甜度档 |

**一句话**：v1.0 把"结构"做对了，v1.1 要把"表述、入口、颜值、覆盖面"收口。

**目标感觉（情感北极星）**：打开首页的瞬间，用户应该感到「**我今天吃了什么，一眼就看得见，而且好看**」——而不是读一串灰色小字做算术。

## 2. Architecture & Solution

### 2.1 目标语义勘误（P1 · 零代码改动）

**先纠正一条被误读的事实**：`1800` **本来就是每日目标**，不是本周目标。

- `app/stores/goal.uts:14` — `const calorieGoal = ref(1800)`，注释「**每日**热量目标」
- `app/pages/settings/Settings.uvue:96` — 设置项名即「**每日**热量目标」
- 首页 `3:22` — 「已摄入 1270 / **1800** kcal」（当天口径）

**问题不在数值，在文案**。「历史趋势 · 本周」+ 横线标签「目标 1800」组合起来，读作"本周目标"。

**结论：v1.1 不动数据模型，只改表述。** 横线标签改为「**每日目标 1800**」。

### 2.2 数据模型

**不做任何改动。** `goalStore.calorieGoal` 仍是**单一每日目标**的 `ref(1800)`，同一时刻只有一个值。

**已知边界（本版不解决，登记为已知限制）**：现有模型**没有"历史每日目标"**，即用户昨天把目标改成 1500、今天改回 1800 后，昨天下钻的达标判定会用**今天的 1800** 去算昨天的数据，结论会失真。

- **v1.1 处置**：写入 `docs/progress.md`「已知限制」，交互上规避（不与用户承诺"历史目标精确"）
- **v1.2+ 候选**：`goal` store 增加 `history: { ts, value }[]`，按 `ts` 回溯当日目标（**本 PRD 不实现，仅登记**）

### 2.3 交互改动清单

#### A. 首页 · 加号入口唯一化（P2）

现状（Ardot 实测）：

- `3:130 Tabbar` 是 `Home(flex1) + 58px 空位 + Profile(flex1)` 三段式
- `3:141 AddButton` 58×58 悬浮球，`x:158.5 y:-14`，两层薄荷投影
- `3:38 EditGoalIcon` 20×20 铅笔（改目标入口）

改造：

1. **删除 `3:141 AddButton`**（含 `3:142` 渐变椭圆 / `3:143` 白色加号向量）
2. **删除 `3:135 Tab-MidSpacer`** → `Tab-Home` 与 `Tab-Profile` 各占 **50%** 宽度（居中对齐）
3. **`3:38` 内容由铅笔换成加号**，触达区 **44×44**（视觉 20×20 不变，遵循 AGENTS.md"头部热区 44×44"既有约定）
4. **改目标入口改道**：设置页 →「每日热量目标」→ 目标设置 Modal（`3:687`，已存在）

#### B. 首页 · Navbar 显示程序名（Boss 项 2）

`3:36 Header` 现有 `3:37 Date`（"9月19日 · 周五"）与 `3:38` 图标。

**设计决策**：**保留日期、追加程序名在左**，而非替换。理由：日期是"今日摄入"这一语境的时间锚点，删掉会让主数字失去时间参照；程序名首页出现一次即可建立品牌感。

结构：`Header = [ 轻律生活(17px SemiBold #0A4F3D) + 日期(12.5px #7A8F88，与程序名同行右侧 gap 8) ] …… 加号图标`

⚠️ **命名确认**：Boss 原话「就叫轻律生活」。项目历史英文名 **EasyLife**。本 PRD 统一采用「**轻律生活**」作为 v1.1 正式中文名登记。

#### D. 首页食物条目加图（P4 · 本条的核心设计）

现状：`3:90 MealDetail` 内三行纯文字，12.5px `#7A8F88`：

```
燕麦片 40g · 150 kcal
水煮蛋 1个 · 120 kcal
全脂牛奶 250ml · 150 kcal
```

三行**无主次、无锚点**，扫视时是一团灰。

**确定方案 · 左置圆图 + 主文 + 右对齐热量**：

| 元素 | 尺寸 | 颜色/字体 |
|---|---|---|
| 图片 | **28×28，`cornerRadius: 8`** | 真实食物图（`assets/icons-final/<catKey>/<id>.webp`）；设计稿内用**带底占位块**（`#E4F0EA` 底 + 10px `#A9BAB3` 类目字） |
| 间距 | 图 → 文 **10px** | — |
| 主文 | 13px SemiBold | `#0A4F3D` —「食物名」 |
| 副文 | 11.5px Regular | `#A9BAB3` —「份量」如 `40g` / `1个` / `250ml` |
| 热量 | 12.5px SemiBold | `#0A7A5C`，`font-variant-numeric: tabular-nums`，右对齐 |

**为什么是"左置圆图"而不是网格卡片**：

1. 现有结构是**餐次时间轴**（`MealIcon` 42px + 竖线），食物图左置后与餐次图标形成**两条纵向对齐列**，结构感立刻出来
2. 网格卡片（图上名下）一屏只能显示 3~4 个食物，且与时间轴结构冲突
3. 左置方案单行成本 = 28px 图 + 10px 间距 = 38px；文字区从 269px 缩至 231px，最长行「全脂牛奶 250ml」12.5px 下约 96px，**余量充足**

**占位策略（Boss 明确要求）**：设计稿内**放带背景的圆角占位**（不用灰方块——灰方块属于 ai-worldclass-design 检查清单 P1「占位素材未替换」的减分项，带底圆角块是可交付的草稿态）。真图在 App 内以 `/static/icons/<catKey>/<id>.webp` 呈现。

#### E. 添加食物 Sheet · 接通「分量/选项」模板体系（P5 · **v1.1 修正版**）

> **[勘误 2026-09-20]** 本条初版写的是「Sheet 只做了奶茶形态，普通食品需要新增 data 模板，多档份量推到 v1.2」。
> **该判断错误，已推翻**——实测 `app/src/data/food_library.json`（347 条）后确认：**数据侧早已完整支持非饮品形态**，
> 缺的是 **App 侧的接通**，不是数据。详见下方实测结论。

**实测结论（推翻原假设）**：

| vessel 分布 | 条数 | | opts 分布 | 条数 |
|---|---|---|---|---|
| `piece`（个） | **170** | | `sweet` | **6** |
| `plate`（份） | 69 | | `topping` | 4 |
| `bag`（包） | 20 | | `sugar_pack` | 2 |
| `bowl_rice`（碗） | 16 | | `syrup_pump` | 2 |
| `bowl_noodle` | 11 | | | |
| `mug` / `bowl_soup` / `pot` | 10 / 7 / 7 | | | |
| `slice` / `cup` / `bottle` / `glass` | 6 / **6** / 6 / 6 | | | |
| `cup_coffee` | 5 | | | |
| `skewer`/`cup_soda`/`shot`/`can`/`glass_wine` | 2/2/2/1/1 | | | |

- **带 `sweet` 的只有 6 条**（`cup` 系列的奶茶/水果茶/杨枝甘露/烧仙草等）
- **其余 341 条（98.3%）本来就是"普通食品形态"**
- 因此：**不存在"要不要新增普通食品形态"的产品选择——它就是默认形态**，`vessel_tpl.yaml` 已定义 16 个模板
- **Toolchain 零改动**，所有???(原以为的)"数据侧前置任务"均取消

**真正的缺口在 App 侧，且已定位到两个 P0 Bug**：

**Bug A · 甜度段对所有食物都渲染（应为条件隐藏）**
- 位置：`app/stores/food_store.ts:163` `sweetOptsOf()` **硬返回 `[]`**
- 连带：`app/components/AddSheet.uvue:46` 判断写的是 `v-if="sweets !== null"`，而 `[] !== null` 恒为真
- 现象：**任何食物**打开 Sheet 都会看到「甜度 · 估算」标题 + **0 个 pill** 的空洞
- 修复两点：① `sweetOptsOf` 改从 `optTpl`（`json.optTpl`）按食物 `opts` 字段真读；② 判断改 `v-if="sweets.length > 0"`

**Bug B · 「个/片/串」类食物热量算错约 80 倍（核心数据错误）**
- 位置：`app/stores/food_store.ts:181` `computeEntry()` 用 `amount / 100` 线性缩放
- 根因：`vessel=piece` 的档位 `amount = 1`、单位是「个」，而食物 `base` 是**每 100g**，
  必须先乘 `pieceWeight` 再缩放；当前代码直接拿 `1 / 100` 当比率
- 实测对照（生成物数据，`base` 取自 `food_library.json`）：

| 食物 | 每100g base | pieceWeight | 正确热量 | 当前代码算出 |
|---|---|---|---|---|
| 馒头 `p017` | 223 | 75 g/个 | **167 kcal** | **2 kcal** |
| 肉包 `p019` | 205 | 80 g/个 | **164 kcal** | **2 kcal** |
| 鸡蛋 `p143` | 144 | 50 g/个 | **72 kcal** | **1 kcal** |
| 苹果 `p230` | 53 | 180 g/个 | **95 kcal** | **1 kcal** |
| 珍珠奶茶 `p270` | 43 /100ml | —（350ml） | 150 kcal | 150 kcal ✓ |
| 米饭 `p001` | 116 | —（150g） | 174 kcal | 174 kcal ✓ |

- **影响面**：库内 `pieceWeight` 非空共 **102 条**；`vessel=piece` 共 **170 条（占 49%）**
- **只对 g/ml 类食物的算法是对的**，按「个/片/串」计的全错
- 修复：`amount` 单位为「个/片/串」时，`amount_g = amount × pieceWeight`，再走 `amount_g / 100`

**UI 呈现（接通后的形态）**：

| 食物类型 | 分量段 | 甜度/选项段 | 说明行 |
|---|---|---|---|
| 奶茶类（`vessel=cup` + `opts: [sweet, topping]`） | 小杯/中杯/大杯 | 甜度 5 档 + 加料多选 | `已按 中杯 500ml · 全糖 计算` |
| 咖啡类（`opts: [sugar_pack]`）| 依 `cup_coffee` 两档 | 加糖 3 档 | `已按 中杯 355ml · 不加糖 计算` |
| 碗/份类（`bowl_rice` / `plate` 等） | 依模板 2~3 档 | **隐藏** | `已按 一碗 200g 计算` |
| 个/片/串类（`piece` / `slice` / `skewer`） | 依模板单档 + 数量步进 | **隐藏** | `已按 1 个（75g）计算` |

> ⚠️ **文案清样（Sample）**：以上四行的具体文案（"一碗 200g"、"1 个（75g）"）是**示例**，实际由 v1.1 占位 + App 接通后的真值决定，非本 PRD 定死。

## 3. Acceptance Criteria (AC)

### AC-1 目标语义（P1）
- [ ] **Given** 用户进入个人中心，**When** 查看柱状图，**Then** 横线标签文案为「**每日目标 1800**」，不出现「本周目标」字样
- [ ] **Given** 用户进入设置页改目标为 1500，**When** 返回首页与个人中心，**Then** 所有目标数字同步为 1500（唯一数据源 `goalStore.calorieGoal`），无任何计算错误

### AC-2 首页入口（P2 + Boss 项 2）
- [ ] **Given** 用户打开首页，**When** 观察底部，**Then** **有且只有两个** tab（首页 / 我的），**无悬浮加号球**，两个 tab 各占 50% 宽度
- [ ] **Given** 用户打开首页，**When** 观察顶部，**Then** 左侧显示「轻律生活」+ 日期，右侧显示**加号**图标（非铅笔）
- [ ] **Given** 用户点击右上角加号，**When** 事件触发，**Then** 打开食物选择 Sheet；系统内**不存在**第二个"新增食物"入口

### AC-3 个人中心（Boss 项 4）
- [ ] **Given** 用户进入个人中心，**When** 观察头图区，**Then** 头像行**右端**有设置图标；点击后进入设置页
- [ ] **Given** 用户进入个人中心并滚动到底，**When** 历史三行结束，**Then** **不存在**「查看全部 30 天记录」这一行，且**底部无异常留白**（内容自然收尾）

### AC-4 首页食物图（P4）
- [ ] **Given** 首页今日餐次列表有 N 条食物，**When** 渲染，**Then** **每一条**左侧都有 28×28 圆角 8px 的食物图，与文本垂直居中对齐
- [ ] **Given** 某食物在库中无对应图，**When** 渲染，**Then** 显示带底圆角占位（**不出现灰色空方块、不出现破图**）

### AC-5 添加食物 Sheet 接通模板体系（P5，Boss 项 5 · 含 2 个 P0 修复）
- [ ] **Given** 用户在食物库选中**奶茶**（`p270`，`vessel=cup` 且 `opts` 含 `sweet`），**When** Sheet 打开，**Then** 出现「分量（小杯/中杯/大杯）」+「甜度 · 估算（5 档，糖粒图标按量显示）」+「餐次（4 档）」，说明行文案含当前容量与甜度
- [ ] **Given** 用户在食物库选中**任一非饮品**（如 `p001 米饭` vessel=`bowl_rice`），**When** Sheet 打开，**Then** **不出现「甜度 · 估算」整段**（不残留标题、不留空行），分量段按 `bowl_rice` 模板渲染小碗/中碗/大碗
- [ ] **Given** 用户在食物库选中**按个计**的食物（如 `p017 馒头`，`vessel=piece`，`pieceWeight=75`），**When** 选中「1个」并确认，**Then** 记录热量为 **167 kcal**（= 223 × 75 / 100），**不是 2 kcal**
- [ ] **Given** 用户选中「鸡蛋 `p143`」（`pieceWeight=50`），**When** 确认，**Then** 记录热量为 **72 kcal**（= 144 × 50 / 100）
- [ ] **Given** 任意 g/ml 类食物，**When** 确认，**Then** 热量与修复前一致（`p270` 中杯 = 150 kcal、`p001` 小碗 = 174 kcal），**不得回归**

## 4. Testing Strategy

**主策略**：**真实 UI 截图比对 + Ardot readback 双通道校验**（本项目既有规范，见 `AGENTS.md`「App 端调试链路」）。

### 4.1 设计侧（Ardot）
- 每批 `batch_edit` 后，用 `batch_read` 复核被改节点的实际属性（尺寸/间距/文案），**不靠"看起来对"下结论**
- 全批改完后调用 `capture_screenshot`（首页 `3:22` + 个人中心 `3:573` + 食物 Sheet `3:367`/`3:494` 一并发起，**配额 2 次以内**），逐张分析后一次性提取所有问题
- 校验点：tab 是否真 50/50、加号触达区是否 44×44、删除 `3:1203` 后底部是否留白、食物图与文本是否垂直居中

### 4.2 App 侧（编译产物实测）
- **禁止**在未跑通构建的情况下宣称完成（AGENTS.md「强制自测红线」）
- 微信开发者工具 + `miniprogram-automator`（端口 9420）：`simulator_screenshot` 取首页与个人中心实拍
- **数据通道**：`page.data()` 断言 `goalStore.calorieGoal` 改动后首页"还能吃"数字同步；断言非饮品食物打开 Sheet 后甜度段不渲染

### 4.3 边界用例（必须覆盖）
| 用例 | 期望 |
|---|---|
| 目标改 1500 → 1900 → 回 1800 | 首页大数字 / 个人中心柱状图 / 设置页副标题三处**始终一致** |
| 用量纲矩阵回归（Boss 项 5 的两个 P0） | 对 `piece`/`slice`/`skewer`/`bag` 类**逐个**验算：热量 = `base × pieceWeight × count / 100`；对 g/ml 类验算回归值不变。样本至少覆盖 `p017/p019/p143/p230`（个）与 `p270/p001`（ml/g）|
| 打开一条估算值食物 | 图 + 名称 + 「估算」标注同时出现，不挤压 |
| 打开无图食物 | 带底占位块，不破图 |
| 首页最长食物名（如「全脂牛奶 250ml」） | 单行不折行、不截断 |

### 4.4 已知限制登记（非缺陷）
- 无"历史每日目标"，跨日下钻的达标判定使用当日目标 —— 写入 `docs/progress.md`「已知限制」
