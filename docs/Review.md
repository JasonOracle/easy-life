# EasyLife 产品逻辑 & UI 方向 · 评审拆解

> 评审日期：2026-09-18
> 评审视角：PM + 产品架构
> 评审对象：EasyLife v1.0 MVP（当前原型 v11 + 现有全部产品文档）
> 评审性质：**批判性复盘**，重点指出不足与改进，不是复述现有方案

---

## 〇、一句话结论

**EasyLife 目前是一个「能用的记录工具」，但还不是一个「能留住人的产品」。**

它把 80% 的精力花在了「录入」上，却忽略了卡路里 App 的真正战场——**反馈与留存**。
同时存在一个致命的产品缺口：**让用户自己填 1800，却不告诉他这个数字是怎么来的。**

---

## 一、产品逻辑拆解

### 1.1 本质：一个「输入 → 反馈」闭环

```
用户吃了东西
    ↓
【输入】记录：搜索 → 选分量 → 选餐次 → 提交
    ↓
【计算】每 100g 热量 × 重量 ÷ 100
    ↓
【输出】可视化：环形图 / 营养素 / 餐次时间轴
    ↓
【反馈】?? ← 这里是空的
    ↓
是否改变下一次进食行为 ← 产品的终极目标
```

**问题在第 5 步。** 目前产品到第 4 步（可视化）就断了——用户看到了数字，但没有被推向「接下来该怎么做」。

### 1.2 价值链：用户真正买什么

用户装一个卡路里 App，买的是这三件事（按重要性排序）：

| 需求 | 用户原话 | EasyLife 现状 |
|------|---------|--------------|
| ① 我还能吃多少？ | "中午吃了 600，晚上还有额度吗" | **❌ 完全没有** |
| ② 我该吃多少？ | "1800 是哪来的？我该设多少" | **❌ 让用户盲填** |
| ③ 我吃了多少？ | "今天摄入多少" | ✅ 做得不错 |

**残酷的事实：产品把唯一做对的那件事，做成了主界面；而用户最关心的两件事，一件没做。**

### 1.3 差异化审视

| 竞品 | 优势 | 劣势 |
|------|------|------|
| 薄荷健康 | 食物库最全、社区、体重曲线 | 重、广告多、强制登录、臃肿 |
| MyFitnessPal | 数据库强、扫码 | 中文食物差、全英文 |
| Keep | 运动闭环 | 卡路里只是附属品 |
| **EasyLife** | **纯本地、零账号、打开即用、无广告** | **功能单薄、无目标指导、无留存机制** |

**结论**：差异化成立，但只打中了「隐私 + 轻量」这一张牌，这张牌能带来首次下载，**带不来长期留存**。

## 二、产品逻辑的不足（按严重程度）

### 🔴 P0-1：缺少目标测算（最严重）

**现状**：1980 时代让用户填。设置弹窗只有一个输入框，默认 1800。

**为什么这是致命的**：
- 用户不知道自己该吃多少 → 随便填 → 数字没有意义 → 整个产品的参考价值崩塌
- 一个不知道目标是否合理的产品，只是一个记账本

**改进**：加一个「目标测算器」
```
性别 / 年龄 / 身高 / 体重 / 活动量
    ↓
BMR（基础代谢，Mifflin-St Jeor 公式）
    ↓
TDEE = BMR × 活动系数（1.2 久坐 ~ 1.9 高强度）
    ↓
按目标给出三档建议：
  减脂  TDEE - 500 kcal
  维持  TDEE
  增肌  TDEE + 300 kcal
    ↓
用户一键采用 / 手动微调
```

这点工作量极小（一个公式 + 一屏表单），但**把产品从「记账本」升级为「顾问」**。

---

### 🔴 P0-2：只显示「已摄入」，不显示「剩余额度」

**现状**：环形图中心是「已摄入 1270」，副标题「已摄入 / 1800」。

**为什么这是错的**：
- "1270" 是个**回顾性数字**，看完就完了
- 用户真正需要的是**决策性数字**："我还能吃 530"

**改进**：环形图主数字改为**剩余额度**
```
       ╭────────────╮
       │   还能吃    │
       │    530 ✏️   │   ← 剩余额度做主数字（大）
       │  已摄入 1270 │   ← 已摄入降级为副信息
       ╰────────────╯
```
超过目标时，切换语境：
```
       ╭────────────╮
       │   已超出    │
       │    120 ⚠️   │   ← 变红/橙，警示色
       │  已摄入 1920 │
       ╰────────────╯
```

**这是整个 UI 最值得改的一处，改动成本几乎为零，产品价值翻倍。**

---

### 🔴 P0-3：食物库覆盖不全时，用户走投无路

**现状**：明确「不支持自定义食物」。搜索无结果 → 记录不了 → 挫败 → 放弃。

**为什么必须解决**：
- 1.8 万条听起来多，但**中餐外卖、家常菜、地方小吃**覆盖必然很差
- 这正是中国用户的主战场（"我妈炒的菜"永远搜不到）
- 这是卡路里 App 的头号流失原因

**改进**：不做完整「自定义食物管理」（同意 MVP 砍掉），但必须开一条**降级通道**：
```
方案 A（推荐）：手动输入热量
  "找不到？直接填" → 输入名称 + 热量数字 → 记为本次记录
  不需要存进食物库，只记这一条

方案 B：常见份量快捷换算
  "一勺油 ≈ 90 kcal"、"一个鸡蛋 ≈ 72 kcal"
  提供常用估算按钮
```
方案 A 是**底线要求**，否则产品有硬伤。

---

### 🟡 P1-4：份量抽象，用户估不准

**现状**：小份 / 中份 / 大份 → 100g / 200g / 300g

**问题**：
- 用户不知道"中份"到底是多大（一只鸡腿？一碗饭？）
- 抽象单位导致估算误差大 → 数据不准 → 信任崩塌

**改进**：份量选项**按食物类型具象化**
| 食物类型 | 当前 | 应改为 |
|---------|------|--------|
| 水果类 | 小/中/大份 | 1个 / 半个 / 100g |
| 主食类 | 小/中/大份 | 1碗 / 半碗 / 100g |
| 饮品类 | 小/中/大份 | 1杯 / 1瓶 / 100ml |
| 肉类 | 小/中/大份 | 1份 / 100g / 自定义 |

并在旁标注**参照物**：
```
🍎 1个     ≈ 拳头大小
🍚 1碗     ≈ 150g 熟重
🥛 1杯     ≈ 250ml
```

让用户凭**视觉记忆**选择，而不是凭重量想象。这是降低录入摩擦的关键细节。

---

### 🟡 P1-5：营养素是"假数据"

**现状**：原型里三大营养素卡片是**硬编码**（蛋白质 65g / 碳水 180g / 脂肪 45g），不随录入变化。

**问题**：这是原型的偷懒，但如果不修正就量产，用户会发现「录了一堆东西，营养素一动不动」→ 直接判定产品是假的。

**改进**：营养素必须像热量一样，**从食物明细实时累加**
```typescript
// Food 已有 protein / carbs / fat（每 100g）
// MealFood 记录 weight
// 累加： nutrient += food[nutrient] × weight / 100
```
数据结构已支持，只需补计算逻辑。

---

### 🟡 P1-6：没有"下一次"的入口 —— 留存机制真空

**现状**：产品是纯粹的被动记录工具，用完即走。

**为什么危险**：卡路里 App 的生死线是**连续记录天数**。典型流失路径：
```
第 1 天 新鲜 → 记录 3 次
第 3 天 忘了 → 断更
第 7 天 想起来 → 数据残缺 → 卸载
```

**没有任何机制阻止这件事发生。**

**改进（本地也能做，不需要服务端）**：
| 机制 | 实现 | 成本 |
|------|------|------|
| 餐点本地通知 | uni 本地定时器，早/中/晚提醒 | 低 |
| 连续打卡 | 首页显示「已连续记录 5 天」徽章 | 极低 |
| 每日小结 | 晚上推送"今日 target 达成" | 中 |
| 周报 | 周日出周度趋势 + 一句点评 | 中 |

**最低成本必做**：连续打卡计数。一个数字，但它是用户回来打开 App 的理由。

---

### 🟡 P1-7：数据只进不出，换机即失

**现状**：纯本地存储，无账号无云端。

**问题**：这是"隐私"的代价，但不能让用户买单。
- 换手机 → 30 天记录全部消失
- 卸载重装 → 归零
- 用户会觉得"我在给你白打工"

**改进**：提供**本地导出/导入**（不需要服务端）
```
设置 → 数据管理
  ├─ 导出备份（生成 JSON，存到系统文件）
  ├─ 从备份导入
  └─ 清空所有数据
```
成本很低，但补齐了"纯本地"方案的最后一块短板。

---

### 🟢 P2-8：只有热量，没有"成果"

**现状**：只有热量进/出，没有体重维度。

**缺失**：用户减肥的真实目标是体重下降，但 App 里看不到。
- 有热量记录、无体重曲线 → 不知道记录有没有"见效"
- 这是长期动力来源

**建议 V1.5 或 V2 加入**：每日体重记录 + 折线图，与热量叠加展示。

---

### 🟢 P2-9：历史记录缺乏"归因"

**现状**：7 天柱状图只显示每日总量。

**改进方向**：点击某天 → 展开当天餐次明细 → 看到"周三超标是因为晚餐吃了火锅"
让数据可解释，而不是只有一根柱子。

## 三、UI 方向拆解

### 3.1 现状评价

**做得好的：**

| 项 | 评价 |
|----|------|
| 3 Tab 结构 | ✅ 克制，符合 MVP 定位 |
| 加号底部弹窗 | ✅ 不打断当前上下文，比跳页面好 |
| 竖向时间轴 | ✅ 本轮最佳改动，直观且有秩序感 |
| 「＋添加食物到早餐」 | ✅ 场景化入口，减少一次切换 |
| 表单式录入 | ✅ 比原来的搜索列表更聚焦 |
| 品牌 badge | ✅ 视觉上有货架感 |

**做得不够的：**

#### ❌ UI-1：首页信息过载，首屏装不下

```
首页堆叠：
  环形图 200px
+ 3 张营养素卡 ~90px
+ 餐次标题
+ 4 个餐次块（每个 ~150px）
= 远超 812px，用户必须滚动才能看到第一餐
```

**核心矛盾**：用户打开 App 最想看的是"我今天吃了啥"，但餐次列表被挤到了折叠线以下。

**改进方案（三选一）：**
- **A（推荐）营养素降级**：营养素卡做成果壳内的一行小字，或折叠进环形图下方的横向条
- **B 营养素移入二级页**：首页只留环形图 + 餐次；营养素点击展开或放到"我的"
- **C 餐次折叠**：默认只展示有记录的餐次，空餐次收起

我倾向 **A + C 组合**：营养素压缩成环形图下方一行「蛋 65g · 碳 180g · 脂 45g」，餐次只展示有内容的。这样首屏能完整看到至少 2 个餐次。

#### ❌ UI-2：环形图与营养素卡在重复表达同一件事

环形图讲"摄入总量"，营养素卡讲"摄入构成"，但它们都在描述同一个"今天"。而两者都缺少**未来视角**（还能吃多少）。

#### ❌ UI-3：空状态完全没设计

新用户第一天打开：
```
🌅 早餐   -- · 暂无记录  0
☀️ 午餐   -- · 暂无记录  0
🌙 晚餐   -- · 暂无记录  0
🍪 加餐   -- · 暂无记录  0
```
**满屏的"暂无记录"，这是最糟糕的第一印象。**

**改进**：
- 首次进入显示引导态："记录第一餐吧 👇" + 高亮早餐卡片
- 未记录的餐次**淡化处理**（降低透明度），而不是硬生生显示 0
- 或默认只展示"当前时间应该记录的那一餐"

#### ❌ UI-4：图标复用的困惑（被忽视的隐患）

1.8 万条食物 → ~180 个图标，意味着**同一个「苹果」图标会出现在几十种食物上**。

用户看到"红富士苹果"和"蛇果"用同一个图标，会觉得"这 App 的数据是糊弄的"。

**改进**：
- 品类图标只作为**兜底/分类标识**，视觉上要弱化（做背景、降低饱和）
- 或者对 Top 200 高频食物做**专属图标**，其余用分类图标
- 品牌食物优先用**品牌 Logo + 真实产品图**（这块已有素材）

#### ❌ UI-5：视觉缺层级，主次不明

目前所有元素的视觉权重接近——环形图、营养素卡、餐次块、meal 图标都在"抢注意力"。

**改进**：明确一条视觉动线
```
① 剩余额度（最大，最醒目）    ← 第一眼：我还能吃多少
② 今日餐次（时间轴）          ← 第二眼：我吃了啥
③ 环形图（装饰+直观占比）     ← 辅助理解
④ 营养素（最弱，可折叠）      ← 专业用户才看
```

#### ❌ UI-6：缺深色模式

一个每天可能被打开 5-10 次的工具 App，晚上（记录晚餐/夜宵时）用白色刺眼。
uni-app x 支持条件跟随系统。**建议至少做一套暗色调色板。**

#### ❌ UI-7：无"超标"的情绪化反馈

现在超过目标时，环形图只是"画满了"，没有任何情绪表达。

**改进**：超标时环形变色（橙 → 红）、或轻微 pulse 提示。让数字有"语气"。

### 3.2 建议的 UI 方向

**设计原则调整为三条：**

1. **决策优先于记录** —— 界面第一任务是回答"我还能吃多少"，不是展示"我吃了多少"
2. **时间轴是主叙事** —— 今日饮食是一条按时间推进的故事线，让它成为首页主角
3. **克制在有数的前提下** —— 砍掉营养素卡的视觉权重，换来首屏的呼吸感

**首页信息架构调整建议：**

```
┌────────────────────────────┐
│  9月18日 周四               │
│                            │
│    ╭──────────────╮        │
│    │   还能吃      │        │  ← ① 剩余额度做主数字
│    │   530 kcal ✏️ │        │
│    │  已摄入 1270  │        │  ← 已摄入降级
│    ╰──────────────╯        │
│  蛋 65g · 碳 180g · 脂 45g  │  ← ② 营养素压成一行
│  ─────────────────────────  │
│  今日餐次                    │
│  🌅 早餐  08:30   312 kcal  │  ← ③ 时间轴主角
│   ● 🍎 苹果 · 1个      52   │
│   ● 🥚 鸡蛋 · 1个     155   │
│  ＋                         │
│  ☀️ 午餐  12:15   542 kcal  │
│   ● 🍚 米饭 · 1碗     260   │
│  ＋                         │
└────────────────────────────┘
```

## 四、需要你拍板的问题

| # | 问题 | 我的建议 |
|---|------|---------|
| 1 | 是否加入 BMR/TDEE 目标测算？ | **强烈建议加**，这是从"工具"到"顾问"的分界线 |
| 2 | 环形图主数字改为剩余额度？ | **建议改**，零成本、高收益 |
| 3 | 是否开放「手动输入热量」降级通道？ | **必须开**，否则外卖/家常菜无法记录 |
| 4 | 营养素卡权重怎么处理？ | 压成一行，或移入二级 |
| 5 | 是否做连续打卡 + 本地提醒？ | 建议做打卡（极低成本），提醒可延后 |
| 6 | 是否做数据导出/导入？ | 建议做，补齐纯本地的短板 |
| 7 | 具象份量（1个/1碗/1杯）替代小中大份？ | 建议改，按食物分类差异化 |
