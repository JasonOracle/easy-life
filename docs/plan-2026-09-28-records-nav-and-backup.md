## 一、甜度选中胶囊阴影加深

### 1.1 现状（已确认）
| 项 | 位置 | 当前值 |
|---|---|---|
| 选中胶囊投影 | `app/components/AddFood.uvue:627`（`.sweet-pill`） | `box-shadow: 0 8rpx 20rpx rgba(10, 79, 61, 0.12)` |
| 胶囊填充 | `AddFood.uvue:264`（`sweetPillStyle`） | `background-color: theme.card`（与底槽同色） |
| 底槽 | `AddFood.uvue:613`（`.sweet-tray`） | `theme.card` 白（2026-09-28 去绿） |

上一轮遗留问题：底槽与胶囊**同为 `theme.card` 白**，选中态只靠这一条 0.12 透明度的阴影区分，偏弱。
老板口径：**不额外加中性加暗底**，改为「阴影适当加深，但要在合理区间」。

### 1.2 参考量级（本仓现有阴影，用于界定「合理区间」）
| 用在哪 | 值 | alpha |
|---|---|---|
| 日历页卡片 `.lr-cal` | `0 8rpx 32rpx rgba(10,79,61,0.06)` | 0.06 |
| 餐次小卡 `.lr-mcard` | `0 4rpx 16rpx rgba(10,79,61,0.04)` | 0.04 |
| AddFood 关闭钮 `:536` | `0 4rpx 16rpx rgba(10,79,61,0.14)` | 0.14 |
| **甜度胶囊（现状）** | `0 8rpx 20rpx rgba(10,79,61,0.12)` | **0.12** |
| AddFood `:685`（浮起/按下态） | `0 16rpx 24rpx rgba(10,79,61,0.35)` | 0.35（过重，不可作常态） |

→ 常态「浮起白块」的合理带＝**alpha 0.16 ~ 0.22**；到 0.35 会变成硬边脏影（也是本仓唯一一条 0.35 被用在按压态的原因）。

### 1.3 建议值（二选一，实测后定）
| 档 | 值 | 说明 |
|---|---|---|
| **A（推荐）** | `0 10rpx 24rpx rgba(10, 79, 61, 0.18)` | 偏移 +2rpx、模糊 +4rpx、透明度 +50%；观感「明显浮起但不脏」 |
| B（更重一档） | `0 12rpx 26rpx rgba(10, 79, 61, 0.22)` | 若 A 在白底上仍读不出来就上这档 |

### 1.4 必须同时处理的两点
1. **暗态单独给值**。`rgba(10,79,61,·)` 是深绿，压在暗色 `theme.card`（暗态卡底）上几乎不可见。
   建议暗态改中性深影：`0 10rpx 24rpx rgba(0, 0, 0, 0.45)`；
   若仍嫌弱，按 TabBar 的经验改「白色光晕」（`0 -6rpx 20rpx rgba(255,255,255,0.9)` 一类）。
   → 实现方式：把 `box-shadow` 从 `.sweet-pill` 静态 style 移到 `sweetPillStyle()` 的 `:style` 按 `isDark` 下发。
2. **顺手确认一条疑似死规则**：`.sweet-pill` 有 `border-width: 1px` + 内联 `border-color: theme.line`，但**没有 `border-style`**。
   按本仓已知坑（Settings 危险卡曾因缺 `border-style` 导致描边完全不渲染），这条描边大概率是死的。
   若阴影加深后还想要一圈边界感，正确的做法是先补 `border-style: solid`——**请老板确认要不要保留这圈描边**。

### 1.5 验收方法
- 真机（MuMu 1280×2772）竖扫选中胶囊边界外的像素，量出「胶囊外 1~8px 环带」与底槽白的亮度差；
  目标：**能稳定量到 ≥ 8 级 R 通道差**（现状量出来的差值很小，正是「看不出来」的量化证据）。
- 三态都要测：默认（五分）/ 最左（无糖）/ 最右（全糖），确认阴影不溢出底槽圆角。

> ⚠️ 待确认点（见 §5-Q1）：老板原话只点名了「今天是月末」这一种情形。

## 三、数据备份 / 恢复

### 3.1 先说结论：**纯本机存储扛不住卸载**
现已落盘的 key 全部位于**应用沙盒**内，卸载时被系统一并清除（Android / iOS 皆然）：

| key | 写入方 | 内容 |
|---|---|---|
| `ct_food_entries_v1` | `stores/food.ts:473` | 全部饮食记录（**核心资产**） |
| `ct_settings_v1` | `stores/settings.ts:5` | 主题/语言/音效/触感/暗色 |
| `ct_goal_v1` | `stores/goal.ts:5` | 每日热量目标 |
| `ct_user_v1` | `stores/user.ts:5` | 昵称 |
| `ct_pending_add` | `pages/home/Home.uvue:523` | 跨页临时态 |

→ 老板要的「卸载 → 重装 → 还能恢复 15 天数据」，必须满足下面三条之一：
**A. 写到「卸载不清除」的位置** ／ **B. 交给外部保管（用户自己的文件/微信/云盘）** ／ **C. 存到云端（需账号 + 后端）**。

### 3.2 方案对比
| 方案 | 跨卸载 | 双端一致 | 额外依赖 | 成本 | 建议 |
|---|---|---|---|---|---|
| **A1 沙盒内多快照** | ✗ | ✓ | 无 | 低 | **必做（L1）**——解决误删/回滚，但抗不住卸载 |
| **A2 写公共目录**（Android `Documents`/`Downloads`） | ✓（仅 Android） | ✗（iOS 沙盒同样随卸载清空） | 存储权限 / Android 10+ 分区存储 | 中 | **待 P0 真机验证**；若通过，老板「重装即可恢复」的理想态在 Android 达成 |
| **B1 系统分享导出 JSON**（`uni.shareWithSystem`）＋ 从文件导入 | ✓ | ✓ | 用户手动一步（发到微信收藏/云盘/文件） | 中 | **推荐主路径** |
| **B2 复制到剪贴板**（JSON 文本） | ✓ | ✓ | 无 | 极低 | 降级兜底，导入侧最稳 |
| **C 云端备份**（自建 / CloudBase） | ✓ | ✓ | 账号体系 + 后端 + 隐私合规 | 高 | 1.0 不做，列 1.1 |
| **D Android Auto Backup**（`allowBackup`） | △ 依赖系统账号，国内不可靠 | Android only | 无 | 低 | 不做 |

> 注意：DCloud 官方社区对「卸载后仍可读」的答复同样是 —— iOS 只有 **Keychain** 能跨卸载，Android 只能把信息存到**外部公共资源**（相册/公共目录）。
> Keychain 容量小、语义是「密钥」，不适合承载记录列表，故不采用。

### 3.3 推荐落地（分三层，一次做完 L1 + B1/B2）
```
L1  本机快照（解决误删、可回滚）
```

### 3.5 数据模型
```ts
// storage key: ct_backup_v1
interface BackupItem {
  id: string          // 时间戳 + 随机后缀，兼作文件名
  createdAt: number   // 备份时刻（列表主行）
  kind: 'auto' | 'manual'
  rangeStart: number  // payload.entries 最早 ts（列表副行）
  rangeEnd: number    // payload.entries 最晚 ts
  dayCount: number    // 去重后的有数据天数
  entryCount: number
  schema: string      // '1.0'，未来 schema 变更用于识别/拒收
  appVersion: string  // '1.0.0'
  payload: {
    entries: FoodEntry[]
    goal: number
    settings?: Partial<SettingsState>   // 可选，默认不带
  }
}
```
- **容量**：15 天 ≈ 50~150 条，单条约 200B → 单份备份 **≈ 10~30KB**；保 **5 份**滚动（LRU 淘汰），总量 < 200KB，安全。
- **触发时机**：① 手动「立即备份」；② **每日首次启动**自动一份（`App.uvue` onLaunch 判定「今日是否已备份」）。
  **不在每次写入后备份**——避免频繁 IO 与快照噪音。
- 恢复逻辑：`food.replaceAll(entries)`（**需新增 action**，`stores/food.ts` 目前只有 `addEntry/removeEntry/clearToday`）→ `goal.setGoal` → 需要时 `settings` 各 setter → 重新 `saveEntries`。

### 3.8 风险 / 合规 / 边界
1. **隐私文案冲突**：设置页现有 `st.shield = 「所有数据仅保存在本机」`。若将来上云（方案 C），**这句必须同步改**，否则是虚假声明。
2. **「自动恢复」的期望管理**：卸载重装后即便文件还在公共目录，**也需要用户回设置页点一下「恢复」**（除非 P0 证明能静默扫到目录并自动导入）。要在需求上跟老板对齐，避免验收时落差。
3. **恢复是覆盖式操作** → 必须先自动快照当前数据；二次确认文案要写清条数。
4. **空库回落种子数据**：`food.ts:485` 在 storage 为空时灌 7 天 SEED_PLAN。恢复流程要保证「先写 storage 再刷内存态」，避免 store 重新初始化时又灌一遍种子。
5. **时区/日键一致性**：区间展示统一走 `dayKeyOf`（`food.ts:411`），不要另写格式化。
6. **方向不可逆**：跨卸载备份一旦引入「公共目录」，Android 上用户手动清理文件仍会删掉 —— 文案里不要承诺「永久保存」。
