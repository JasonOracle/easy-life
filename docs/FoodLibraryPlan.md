## 二、数据来源与合规（红线先画）

**事实性数据（热量数值）本身不受版权保护，但数据库编排受保护。**

| 来源 | 授权 | 覆盖 | 用法 |
|---|---|---|---|
| 中国食物成分表（第 2/6 版） | 事实数据，业界通用 | 基础食材 800+ | 主食数值来源，不自称官方 |
| USDA FoodData Central | **Public Domain**（美国政府作品） | 西式/进口 2000+ | 补充，需单位换算 |
| Open Food Facts | **ODbL + CC BY-SA**（需署名 + 保持开放） | 包装食品/条码 | 合规但要署名，中文覆盖有限 |
| 品牌官网营养标签 | 公开事实数据 | 品牌 500–1000 | 逐条记录来源 URL + 抓取日期 |
| LLM 批量生成 + 抽样校验 | 自建数据 | 中式菜品 / 长尾 | **必须标注"估算"** |

**红线（不做）**：不爬取薄荷健康 / Keep / 乐动力等竞品数据库（有判例，且是竞品核心资产）。

**备选**：FatSecret Platform API（付费授权、有配额），若自建成本过高可作为商业方案评估。

## 三、数据分层（v1.0 实际：按置信度三档）

v1.0 的 347 条**不分层**，而是**每条数据自带 `confidence`（置信度）与 `basis`（依据类型）**：

| 置信度 | 含义 | 条数 | 依据类型 | UI 表现 |
|---|---|---|---|---|
| **conf=3** | 权威可核 | 179 | `composition_table`（成分表标准值） | 正常显示 |
| **conf=2** | 较可靠 | 163 | `recipe_estimate`（配方推算，附可复核拆解） | 正常显示 |
| **conf=1** | 估算 | 11 | `recipe_estimate` / `rough_estimate`（波动大） | 详情页标「估算值，仅供参考」 |

**取值方法（按「有没有权威数据」分流）**：
- **基础食材**（蔬果肉蛋奶、米面）→ 成分表标准值：这类数值是**客观常量**，不因店而异
- **中式菜品 / 复合主食 / 现制饮品** → **配方推算**，并写出可复核的配方拆解
  （如宫保鸡丁 = 鸡胸肉 60g + 花生米 20g + 油 10g + 糖 5g + 酱油 5g，总约 130g 成品）
- **麻辣烫 / 火锅** 这类极度依赖点单的 → 粗略估算 + `conf=1`

> **为什么不再用「L1–L4 四层」**：那套分层是为 18,000 条库设计的。
> 347 条精品库里每条都是高频食物，**逐条标置信度比分层更精确**——分层会让「同一层里有的准有的不准」。
>
> ⚠️ **实测质量**（该轮 347 条口径）：经「分类区间 + 宏量配平」双重自动筛查，**错误率 1.4%（5/347）且已全部修正**。
> 失误模式集中在**量纲**（把「每份」的热量误标为「每 100ml」）—— 这是将来扩充数据时要重点防的。
> **补录的 p348–p353 六条同样过自动校验（`validate.py`），但尚未过人工核对**——
> `nutrition_checklist.md` 的 30 条优先核对项截至 2026-09-22 **一条都没核过**（进度 0/30，见「六、生产流水线」④）。

## 三·五、贴近生活的品类：现制饮品 / 连锁品牌 / 外卖（最高价值区）

### 为什么重心要移过来

基础食材（苹果 52、米饭 116）用户自己估得八九不离十，边际价值很低。
真正估不准、且最想记录的是——**一杯奶茶 300–700 kcal，占女性日需约 1/3，用户完全没概念**。

> **说不清的食物，才是 EasyLife 的价值所在。**

### 品类清单（v1.0 建议覆盖）

| 品类 | 代表品牌 | 备注 |
|---|---|---|
| **现制茶饮** | 喜茶、奈雪、蜜雪冰城、茶百道、古茗、霸王茶姬、沪上阿姨、CoCo | 中国最高频，变量最多 |
| **现制咖啡** | 瑞幸、星巴克、库迪、Manner、Tims | 奶咖 vs 美式、风味糖浆差异大 |
| **连锁快餐** | 麦当劳、肯德基、汉堡王、塔斯汀、华莱士、德克士 | 官方营养标签公开，质量最高 |
| **中式连锁** | 老乡鸡、乡村基、和府捞面、杨国福、张亮麻辣烫、真功夫 | 份量差异大，需"份"模型 |
| **便利店** | 7-11、罗森、全家（饭团 / 便当 / 三明治） | + 包装食品条码 |
| **包装零食** | 薯片、饼干、辣条、面包、酸奶 | Open Food Facts 补齐 |

### ⚠️ 奶茶不是一条数据，是一棵配置树

一杯"多肉葡萄"的热量 = 杯型（中/大）× 甜度（全糖/七分/半糖/三分/无糖）
× 温度（热/常温/少冰/去冰）× 加料（珍珠/芋泥/奶盖/椰果/布丁）。
全组合展开是**单品几百条**，既不可能穷举，也不该穷举。

**用 base + modifier 模型**（组合计算，不预生成）：

```
final = base(品牌 + 单品 + 杯型)
      + modifier(甜度档位)     // 全糖 +0 / 半糖 −35% / 无糖 −70%（按糖浆占比）
      + Σ modifier(小料)       // 珍珠 +120 / 奶盖 +180 / 椰果 +60（量级示意，待核实）
      + modifier(温度)         // 热饮多用奶与糖浆，+10~20
```

- **数据量**：1 个单品 = 1 条 base + N 条可跨单品复用的 modifier，而非几百条展开
- **甜度档位各家定义不同**（"三分糖" ≠ 30% 糖）→ 统一归一为 5 档，并**标注为估算**
- **数值来源优先级**：品牌官方营养标签 > 公开检测/实测 > 按配方估算（必须标"估算"）
- 上表 modifier 数值仅为**量级示意**，落地时必须以官方标签或实测替换

### 对原型的影响：需要"配置式录入"

现有添加弹窗只有「分量 + 餐次」，撑不住奶茶。需要新增：

- 杯型：分段控件（中 / 大）
- 甜度：分段控件（全糖 / 七分 / 半糖 / 三分 / 无糖）
- 小料：chips 多选（珍珠 / 椰果 / 芋泥 / 奶盖 / 布丁）

每选一项，热量实时更新——**这恰好是液滴隐喻最好的场景：加一份奶盖，水位涨一截**。

### 维护成本

连锁品牌菜单 1–3 个月就上新/下架 → v1.0 只做 **Top 品牌 × Top 单品**（每家 15–30 款，
约 600–900 条），不追全菜单；菜单变更走 v1.1 的增量更新包。

## 四、数据结构（v1.0 字段）

```jsonc
{
  "v": "1.0.0",                    // 库版本，供后续增量更新
  // 列式存储：比对象数组小 40%，且可整块 mmap
  "ids":   ["f0001", "f0002"],
  "names": ["苹果", "米饭（熟）"],
  "alias": ["apple|苹果|红富士", "米饭|白饭|大米饭"],
  "pinyin":["pingguo|pg", "mifan|mf"],
  "cal":   [52, 116],              // kcal / 100g（或 100ml）
  "p":     [0.3, 2.6], "c": [14, 25.9], "f": [0.2, 0.3],   // 蛋白/碳水/脂肪
  "cat":   [1, 4],                 // 分类枚举
  "brand": [0, 0],                 // 0=无品牌
  "state": [0, 1],                 // 0=生鲜 1=熟 2=干货  ← 见下方铁律
  "edible":[0.76, 1.0],            // 可食部系数（苹果带皮 76%）
  "unit":  [3, 7],                 // 指向 serving 模板
  "img":   ["t0128", "c04"],       // t=专属真图 c=品类兜底图
  "src":   [1, 1], "conf": [3, 3]  // 来源枚举 / 置信度 3=高 2=中 1=估算
}
```

### 三条数据铁律（踩了就是差评）

1. **生熟必须分开**：大米（生）346 kcal/100g ≠ 米饭（熟）116 kcal/100g。
   用户搜"米饭"给出生米数值，差 3 倍——这是 calorie app 最高频的投诉来源。
2. **可食部系数**：鸡腿（带骨）vs 鸡腿肉、苹果（带皮）vs 苹果肉，必须显式建模。
3. **份量单位优先于重量**：中国用户不会称"138g 米饭"，会选"一碗"。
   每条内置容器份量：`个 / 根 / 碗 / 杯 / 片 / 份 / 勺`，并给出克重。

### 置信度要敢显示

`conf=1`（估算）的食物，在详情页标一行小字「估算值，仅供参考」。
**踏实**的情感北极星要求：不装作精确。宁可承认是估算，也不给一个假精确的 563 kcal。

## 五、搜索（体验的真正分水岭）

**347 条**纯前端搜索，必须做到零延迟：

| 要求 | 实现 |
|---|---|
| 输入即出结果 | 预建倒排索引：首字 / 拼音全拼 / 拼音首字母 → id 列表 |
| 中文容错 | 番茄 = 西红柿 = 圣女果；错别字（"鸡旦"→"鸡蛋"） |
| 拼音 | `xhs` → 西红柿；`jichi` → 鸡翅 |
| 排序权重 | 历史记录 > 名称前缀 > 分词匹配 > 品类热度 |
| 性能 | 首次输入响应 < 16ms（347 条 + `alias` 后索引常驻内存约 30KB，远低于原估 1.5MB） |

**验收标准**：100 条真实查询词测试集，Top1 命中率 ≥ 85%。

> **347 条下的新要求**：条数少了，**覆盖面的短板更明显** —— 用户搜不到时的兜底体验比命中率更重要。
> 所以记录级热量覆盖（10.3）与空态「自己创建」入口（第十一章）在 v1.0 的权重反而上升。

## 十、v2.1 决策更新：v1.0 范围收敛（Boss 拍板）

### 10.1 v1.0 食物库只做三件事

1. **基础食材 + 常见食物 + 中式成品菜**（**347 条**，数据全量内置），每个食物一张专属图
2. **奶茶一个品类**（不区分品牌，通用图标），支持杯型选择
3. **用户可自己补充热量**（手动输入通道，记录级）

品牌（喜茶/瑞幸/麦当劳…）全部后置到 v1.1 —— 维护成本高，且 v1.0 先验证核心闭环。
**用户自定义规格 / 模板同样不做**（理由见开头「v1.0 用户可编辑范围」）。

### 10.2 计量器具（vessel）模型 ⭐ 新增

**为什么不能只加一个字段**：奶茶中杯 500ml ≠ 咖啡中杯 354ml ≠ 可乐中杯 330ml。
杯型是**通用概念，具体容量是食物自己的**。

**解法：模板 + 覆盖**

```jsonc
// ① 器具模板（全局一份，UI 靠它生成分段控件）
"vesselTpl": {
  "cup":  { "label": "杯", "sizes": [ {"k":"小杯","amount":350,"unit":"ml"},
                                      {"k":"中杯","amount":500,"unit":"ml"},
                                      {"k":"大杯","amount":700,"unit":"ml"} ] },
  "bowl": { "label": "碗", "sizes": [ {"k":"小碗","amount":200,"unit":"g"},
                                      {"k":"大碗","amount":400,"unit":"g"} ] },
  "piece":{ "label": "个", "sizes": [ {"k":"1个","amount":1,"unit":"个"} ] }
}

// ② 食物条目：引用模板 + 可选覆盖（奶茶就用默认，咖啡覆盖成自己的容量）
{
  "id": "d0001",
  "name": "奶茶",
  "cat": "饮品",
  "img": "c_tea",                       // 通用图标，不区分品牌
  "base": { "cal": 65, "per": 100, "unit": "ml" },   // 每 100ml 的热量
  "vessel": "cup",                      // ← 引用器具模板
  "override": null,                     // 需要时覆盖：{"中杯":500,"大杯":700}
  "conf": 1,                            // 估算值
  "editable": true                      // 允许用户手改热量
}
```

**热量计算**：`cal = base.cal × vessel.amount / base.per`

- 有 `vessel` → UI 渲染**分段控件**（小/中/大）
- 无 `vessel` → 退回普通份量单选（现有逻辑不变）
- 后续加甜度/小料时，只需在 `base` 之上叠 `modifiers`，结构不用改

**⚠️ 奶茶热量必须是"大致值"并明示估算**：不同店配方差异极大，
v1.0 给一个中位数量级即可，UI 标「估算，可自行调整」——符合"踏实"北极星。

### 10.2.1 食物选项组（optionGroups）⭐ Boss 追加：甜度

**需求**：选到奶茶这类食物时，自动多出「几分糖」选项。

**关键判断：不要给奶茶硬编码一个字段。**
甜度是奶茶的，但"选项随食物变化"这件事是通用的——咖啡的奶量、面的硬度、米饭的生熟，
都是同一个模式。硬编码会让第二个品类来时被迫重构。

**解法：选项模板 + 食物引用**（与 vessel 同构）

```jsonc
"optTpl": {
  "sweet": {
    "key": "sweet", "label": "甜度", "def": "full",
    "hint": "甜度为估算值，各品牌糖量标准不同",
    "opts": [
      { "k":"none",  "name":"无糖", "delta":-110 },
      { "k":"light", "name":"三分", "delta":-80  },
      { "k":"half",  "name":"五分", "delta":-55  },
      { "k":"less",  "name":"七分", "delta":-30  },
      { "k":"full",  "name":"全糖", "delta":0    }
    ]
  }
}

// 食物侧只写引用
{ "name":"奶茶", "base":{"cal":65,"per":100,"unit":"ml"},
  "vessel":"cup", "opts":["sweet"], "conf":0 }
```

**三个必须遵守的建模规则**

| 规则 | 说明 |
|---|---|
| **delta 是绝对值，不是百分比** | 糖的热量占总量约 1/3，用百分比算在小杯上会失真。绝对值 `-110 kcal` 更可控、更好解释 |
| **按容量线性缩放** | `delta × (实际容量 / 基准 500ml)`。大杯少糖比小杯少糖省得更多，符合直觉 |
| **档位归一成 5 档** | 各品牌"三分糖"不是一回事（喜茶 ≠ 蜜雪），统一归一并**明确标估算** |

**计算**：`cal = base.cal × amount / per + Σ delta × (amount / 基准)`

**实测数值（奶茶 65 kcal/100ml）**

|  | 无糖 | 三分 | 五分 | 七分 | 全糖 |
|---|---|---|---|---|---|
| 小杯 350ml | 151 | 172 | 189 | 207 | 228 |
| 中杯 500ml | 215 | 245 | 270 | 295 | 325 |
| 大杯 700ml | 301 | 343 | 378 | 413 | 455 |

**UI 表现**（原型 v17 已落地）
- 选项行**按食物自动出现**：选奶茶 → 出现甜度分段；选苹果 → 不出现
- 分段控件 5 档，选中薄荷填充；下方 10.5px 灰字 hint 说明估算
- 切换甜度 → 热量数字弹跳 + 液滴晃动，**看得见的差别**就是记忆点
- 热量旁「改」按钮 → 记录级覆盖，改完标「已调整」

### 10.3 用户补充热量（记录级覆盖）

| 项 | 设计 |
|---|---|
| 入口 | 添加弹窗的热量数值旁一个「改」按钮 |
| 存储 | `record.userCal`（记录级），**不写回食物库** |
| 显示 | 该条记录标「已调整」小角标 |
| 复用 | 下次再选同一食物，仍给库里的值（不记住用户覆盖，避免"越改越偏"） |

> 这样既满足了"用户能补"，又守住了"不支持自建食物库"的决策边界——
> 用户改的是**这一次**记录，不是**这个食物**。

### 10.4 工程是否分两部分？**要分，但同仓，不分仓** ⭐

```
EasyLife/
├── app/                      # uni-app x 应用（日常开发）
│   ├── pages/ ...
│   └── src/data/
│       └── food_library.json # ⚠️ 生成物，绝不手写（实际落地路径；旧 app/data/ 目录已删除）
└── toolchain/                # 数据处理脚本（不进 App 包）
    ├── sources/              # 原始数据源（人可读，可 review）
    │   └── *.yaml            # 现为 6 份：清单 / 营养 / 份量引用 / 生图槽位 / vessel 模板 / opts 模板
    ├── schema.ts | .json     # 数据格式定义（单一事实来源）
    ├── validate.py           # 校验：必填/异常值/单位统一/交叉核对
    ├── build.py              # 打包：列式压缩 + 倒排索引 + 版本号
    └── dist/                 # 产出 → 复制到 app/src/data/
```

**为什么要分**

| 理由 | 说明 |
|---|---|
| 语言/运行时不同 | 数据处理用 Python（pandas/openpyxl），App 是 uni-app x + TS |
| 生命周期不同 | 数据一个月动一次，App 天天改 |
| 依赖隔离 | 数据处理依赖绝不污染 App 构建链 |
| 产物单向流动 | `toolchain → app/src/data`，App 只读不写 |

**为什么不分仓**

数据与 App 的字段必须同步演进。分仓会出现"数据 schema 改了、App 没跟上"的静默错位。
同仓可以让 CI 在 build 时校验 schema 版本。

**三条铁律**

1. **App 里绝不手写食物数据** —— `food_library.json` 标记为 generated，改数据必须走 toolchain
2. **每次产出带指纹** —— `libraryVersion` + 生成时间 + 来源清单 + 条数，出事能回溯
3. **启动时校验 schema** —— App 启动时比对 schema 版本，不匹配直接报错，不静默出错

**不要过早自动化**：v1.0 只有奶茶一个品类的器具，
先在 `sources/` 里**手工维护人可读的 YAML**，脚本只做校验和打包。
等品类真正多起来（>50 个需要器具的食物），再上采集自动化。

## 十一、v1.1 自建食物：v1.0 必须做完的预留（Boss 拍板）

### 11.1 决策

**v1.0 不做自建食物，v1.1 做**——用户自建后，下次直接就能选到。

**但 v1.0 的数据设计必须为 v1.1 留好。** 这不是提前开发功能，
而是避免 v1.1 上线时老用户的数据需要迁移、甚至损坏。

### 11.2 现在不动的代价：三类「改不回来」的问题

| 现在不预留 | v1.1 上线时的后果 |
|---|---|
| **记录只存 `foodId`** | 公共库更新/重排 ID 后，历史记录查不到食物 → 名字空白或错乱。**老数据永久无法修复**——当时吃了什么，已经没人知道了 |
| 不隔离 ID 命名空间 | 自建条目与公共库 ID 撞车，更新库时被静默覆盖 |
| 备份文件不带版本 | v1.0 的备份拿到 v1.1 恢复 → 结构不认识 → 崩溃或静默丢数据 |

第一类最致命：**数据一旦以残缺形式落盘，后面永远补不回来**。
所以这五条必须在 v1.0 发布前落地，不能等 v1.1。

### 11.3 v1.0 就要落地的五条预留

**① 记录存冗余快照（最关键）**

```jsonc
record = {
  "foodId": "p0123",
  "foodName": "奶茶",          // ← 快照，库更新也不变
  "source": "library",          // v1.1 自建 = "user"
  "schemaVersion": 1,
  "portionName": "中杯 · 五分糖", "weight": 500, "unit": "ml",
  "calories": 270,
  "userCal": null               // 记录级覆盖
}
```

历史记录显示的是「当时吃了什么」，不依赖当前库里还有什么。

**② ID 命名空间规则**：公共 `p` 前缀、自建 `u` 前缀（如 `u_1737xxxx`）。
v1.1 第一条自建起就带 `u` 前缀 —— **前缀不同即天然隔离，公共库数字 ID 不用迁移。**

**③ `schemaVersion` 字段**：v1.0 = 1。启动时读到更高版本 → 只读显示、不崩、不丢数据。

**④ `source` 字段**：`library` / `user`。v1.0 全是 `library` → v1.1 老数据**零迁移**。

**⑤ 备份文件带 `schemaVersion`**：恢复时做兼容判断。
低版本备份 → 高版本恢复：补默认值；高版本 → 低版本：拒绝并提示。

### 11.4 一个开关，不要散落的 if

```ts
const USER_FOOD_ENABLED = false;   // v1.1 改成 true
```

UI 只查这一个常量。**禁止**在各处写 `if (支持自建)` 的临时判断——v1.1 一定会漏改某处。

### 11.5 UI 占位 + 埋点收益（v1.0 现在就做）

搜索空态放「＋ 自己创建」，点击提示 v1.1 上线。三个收益：

1. v1.1 启用时入口不突兀（用户早见过这个位置）
2. **埋点收集「搜不到的词」** = 公共库补录优先级最真实的依据，比拍脑袋准
3. 缓解流失：用户知道"以后能建"，而不是"这个 App 不支持"

### 11.6 v1.1 自建食物字段（现在定死，v1.0 不实现）

```jsonc
{
  "id": "u_1737xxxx", "name": "妈妈做的红烧肉", "cat": "家常菜",
  "base": { "cal": 220, "per": 100, "unit": "g" },
  "vessel": null, "portions": [{ "name": "一碗", "weight": 250 }],
  "icon": "c_meat", "source": "user",
  "createdAt": "...", "useCount": 12
}
```

- **与公共库同 schema** —— vessel / portion / opts 机制完全复用（v1.0 已建好，不用重写）
- `useCount` 用于排序：**自建食物搜索优先级高于公共库**（用户自己录的最贴近自己）
- 图标从品类图里选，**不支持上传**（上传涉及存储与审核，v1.1 不值当）

### 11.7 天然升级路径：从 `userCal` 到自建食物

v1.0 已有「记录级热量覆盖」。
**同一食物被手动改过 3 次 → 提示"要不要存为我的食物？"**

用户不用从零填表，转化路径最短，而且数据是他自己反复验证过的——
比让用户凭空创建一条更可靠。

### 11.8 数据质量风险与应对

用户可能随手填「一碗米饭 500 kcal」（实际约 200）。

- ❌ **不做强制校验 / 弹警告**：打扰，且违背"踏实"的不打扰原则
- ✅ 「我的食物」列表显示「你记录过 N 次」，长期偏差由用户自己发现
- ✅ 搜索排序自建优先，但**不编造营养明细** —— 自建条目缺失的字段显示「—」

### 11.9 现在**不要**做的事

- 不写自建食物的编辑 / 存储逻辑（v1.1 才写，避免死代码和二次返工）
- 不迁移公共库 ID（前缀不同即隔离，迁移是白做功）
- 不在 v1.0 埋「v1.1 会支持」的空承诺弹窗（只放静态入口 + Toast，不打扰）

| v1.0 搜索空态入口占位 | ✅ 原型已落地（点击提示 v1.1） |
